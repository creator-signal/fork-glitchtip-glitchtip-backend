# Self-hosted support flow (backend)

This doc describes the backend changes that support the self-hosted-support
feature: letting a self-hosted GlitchTip user (a) store a license key on
their organization, (b) view their Stripe-hosted invoice for proof of
purchase, and (c) recover their license key by email if they lost it.

The frontend lives in two repos: the in-app UI (license card in Org Settings,
certificate modal, support nav) in `glitchtip-frontend`, and the public
`/support` recovery page in the `marketing` branch of the same repo. This
doc only covers the backend.

## Architecture

Three trust zones, one user-visible flow:

```
┌─────────────────────────┐     ┌──────────────────────────┐     ┌─────────────────────────┐
│  Self-hosted instance   │     │  glitchtip.com (static)  │     │  app.glitchtip.com      │
│  (untrusted)            │     │  (trusted, limited JS)   │     │  (trusted, full backend)│
│                         │     │                          │     │                         │
│  Stores: org            │     │  /support page           │────▶│  /api/0/billing/        │
│    .license_key         │────▶│  • License-recovery form │     │     license-invoice/    │
│  Sends user to          │     │  • Posts to backend      │     │  /api/0/billing/        │
│    license-invoice/     │     │                          │     │     customer-by-email/  │
│                         │     │  Stores: nothing         │     │                         │
│                         │     │                          │     │  Calls Stripe API       │
└─────────────────────────┘     └──────────────────────────┘     └──────────┬──────────────┘
                                                                            │
                                                                            ▼
                                                                ┌─────────────────────────┐
                                                                │  Stripe                 │
                                                                │  • customer lookup      │
                                                                │  • hosted invoice URL   │
                                                                └─────────────────────────┘
```

Self-hosted instances never talk to Stripe directly. They route through two
public endpoints on `app.glitchtip.com` (the only place that holds Stripe
credentials).

## Model changes

`Organization` gained two fields ([apps/organizations_ext/models.py:189-190](apps/organizations_ext/models.py#L189-L190)):

- `license_key: CharField(255, blank=True, default="")` — the Stripe customer
  ID (`cus_xxx`). Free-form opaque identifier; we never parse or validate it
  beyond format on the API side. Same sizing as the existing
  `stripe_customer_id` field's pattern but with the `default=""` form used by
  the schemas that flow through ninja.
- `license_billing_email: EmailField(blank=True, default="")` — billing
  contact for support lookups. Optional; not currently used by any logic, but
  the org PUT accepts it so the frontend can collect both at once.

Migration: [apps/organizations_ext/migrations/0012_organization_license_fields.py](apps/organizations_ext/migrations/0012_organization_license_fields.py).
Auto-generated by `makemigrations`. Both fields default to empty string,
so the migration is non-destructive on existing rows.

## Schema and API surface

### Organization writable fields ([apps/organizations_ext/schema.py:16-23](apps/organizations_ext/schema.py#L16-L23))

`OrganizationInSchema` now includes `license_key` and `license_billing_email`
in `Meta.fields`. Both are optional (default empty string at the model layer),
so the existing frontend payload that sends only `{name, ...}` continues to
work; the new fields can be set independently.

The PUT handler ([apps/organizations_ext/api.py:128](apps/organizations_ext/api.py#L128))
was switched from `payload.dict()` to `payload.dict(exclude_unset=True)`.
Without this, a client sending `{name, licenseKey}` would silently clobber
`licenseBillingEmail` back to its default empty string (and vice versa).
The new form gives true partial-update semantics, matching the existing
pattern in [apps/projects/api.py:122](apps/projects/api.py#L122).

### Organization detail response ([apps/teams/schema.py:63-67](apps/teams/schema.py#L63-L67))

`OrganizationDetailSchema` returns the two new fields on `GET /api/0/organizations/{slug}/`.
The list endpoint (`OrganizationSchema`) intentionally does NOT include them
— small surface area, only the detail view needs them.

### New: `GET /api/0/billing/license-invoice/`

Public, unauthenticated. Takes `customer_id=cus_xxx` query param. Looks up
the customer's most recent Stripe invoice and 302s to its `hosted_invoice_url`
(Stripe's "Invoice paid" receipt page with download buttons). Falls back to
the configured `STRIPE_PORTAL_LOGIN_URL` for unknown customers, customers
with no invoices, or invoices without a hosted URL.

[apps/stripe/billing_api.py](apps/stripe/billing_api.py)

Rate-limited 10/min per IP. Lives at `/api/0/billing/...` (separate router
from `/api/0/stripe/...` because the latter requires auth on every endpoint).

### New: `POST /api/0/billing/customer-by-email/`

Public, unauthenticated. Body `{"email": "user@example.com"}`. Looks up the
Stripe customer by email; if matched, sends them an email containing their
license key. **Always returns `200 {"ok": true}` on syntactically valid input**
regardless of match status — anti-enumeration.

[apps/stripe/billing_api.py](apps/stripe/billing_api.py)

Two-tier rate limit:

- 10/hr per IP (forgiving for corporate NAT)
- 3/hr per email, normalized to lowercase + trim (caps single-inbox
  harassment regardless of source IP)

The Stripe lookup and email send happen in a queued `django-tasks` task
([apps/stripe/tasks.py](apps/stripe/tasks.py)) so response timing doesn't
leak match-vs-no-match. Only `StripeResourceNotFound` is caught silently;
transient errors (5xx, network) propagate so the task runner retries with
backoff. The email is sent to the address Stripe has on file for the matched
customer, NOT the caller-supplied address — closes a subtle leak where
Stripe's case-insensitive lookup could route to a different inbox, and
where a customer with `email=None` on file would otherwise receive their
key at the caller's inbox.

## Supporting code

- [apps/stripe/client.py](apps/stripe/client.py): added
  `fetch_customer_by_email(email)` and `fetch_latest_invoice_for_customer(customer_id)`.
  Both use the existing async aiohttp client (`stripe_get`). Customer lookup
  fetches `limit=3` and warns on multi-match (the rare duplicate-customer case),
  picking the newest.

  Stripe's `400 + code: "resource_missing"` to `StripeResourceNotFound` (Stripe

  the license-invoice endpoint.
- [apps/stripe/email.py](apps/stripe/email.py): `LicenseKeyEmail` extends
  `GlitchTipEmail` (NOT `DetailEmail` — there's no model row, just an email
  address and a key string).
- [apps/stripe/templates/stripe/license-key.{txt,html,subject.txt}](apps/stripe/templates/stripe/):
  Plain-text + HTML multipart, minimal styling, mentions the paste target
  ("Organization Settings → Support License").
- [apps/stripe/tasks.py](apps/stripe/tasks.py): one `@task`,
  `send_license_key_email_by_lookup`. Pattern mirrors
  [apps/organizations_ext/tasks.py:155-157](apps/organizations_ext/tasks.py#L155-L157).
- [glitchtip/settings.py:660-665](glitchtip/settings.py#L660-L665): new

## Security properties

1. **Anti-enumeration on `customer-by-email`.** Response body, status code,
   and timing are identical for "match" / "no match" / "Stripe transient
   error." Whether someone has a GlitchTip subscription is only revealed by
   the email arriving in their inbox.
2. **No license-key delivery to caller-controlled inboxes.** Even if a
   malicious caller submits `attacker@evil.com`, the email goes to whatever
   address Stripe has on file for the matched customer (or doesn't send at
   all if Stripe has no email).
3. **Atomic rate limiting.** The `_throttle` helper uses `cache.aadd` for the
   first slot (only one concurrent caller wins) and `cache.aincr` for
   subsequent slots (atomic increment-and-return). Verified under concurrent
   load: 15 simultaneous requests against a 10/hr limit produced exactly 10
   200s and 5 429s.
4. **Retries on transient Stripe failures.** A 503 from Stripe doesn't
   silently lose the email request — the queued task retries with backoff.

## Dev / local testing

A dual-stack docker compose setup is documented at
[docs/local-license-invoice-dual-stack.md](local-license-invoice-dual-stack.md).
Briefly: it runs a self-hosted-style backend on `:8000` (no Stripe creds,

### Tests

- **138 tests pass** in `apps.stripe` + `apps.organizations_ext` combined.
- **Full suite**: 1054/1055 pass. The single failure is `apps.issue_events.tests.test_issue_event_api.IssueEventAPITestCase.test_retrieve`,

### End-to-end verification against real Stripe

Both public endpoints were exercised against a Stripe sandbox account during
development, not just mocked:

- `GET /api/0/billing/license-invoice/` with a real customer that has a paid
  $1 invoice returns 302 to `https://invoice.stripe.com/i/...` — the
  "Invoice paid" hosted page with download buttons.
- `GET /api/0/billing/license-invoice/` with unknown / no-invoices customers
  returns 302 to the configured fallback URL.
- `POST /api/0/billing/customer-by-email/` with a real customer's email
  renders the license-key email containing the correct `cus_xxx`, addressed
  to the Stripe-verified email (NOT the caller-supplied one).
- `POST /api/0/billing/customer-by-email/` with an unmatched email returns
  the same `200 {"ok": true}` with no email sent — anti-enumeration property
  verified end-to-end, not just at the unit-test layer.

### Convention review against existing code

The changeset was compared against existing patterns in the repo:

  for the invite email, adapted for the no-model case.
- Tasks module lives at `apps/stripe/tasks.py` — matches every other app's

- Templates live at `apps/stripe/templates/stripe/<name>.{txt,html,subject.txt}`

- `@task` + `aenqueue` usage matches
  [apps/organizations_ext/tasks.py:155-157](apps/organizations_ext/tasks.py#L155-L157)
  exactly.
- Rate-limit cache pattern is the same `cache.aadd` / `cache.aincr` primitive
  that the existing org-invite throttle in
  [apps/organizations_ext/api.py:238-248](apps/organizations_ext/api.py#L238-L248)

### Multi-agent review

Three independent reviewers ran against this code before staging: one for
correctness/security, one for codebase-fit, one for design-soundness. Their
findings were adjudicated and acted on:

- **Fixed**: race condition in the throttle helper (switched to atomic
  `aadd`/`aincr`), email sent to caller-submitted address instead of
  `customer.email` (potential enumeration leak when `customer.email` is
  `None`), missing task retry on transient Stripe errors (now only swallows
  `StripeResourceNotFound`), per-email rate limit looser than per-IP
  (flipped to 10/hr IP, 3/hr email), and dead-code documentation claim about
  multi-customer matches (now actually warns).
- **Deferred with reasoning**: hashed audit log of who requested which email
  (defer until forensic need actually arises), CAPTCHA on the public
  endpoint (rate limit + atomic throttle covers the obvious attacks; if
  edge-level bot rules are needed, that's an ops decision, not a code
  change), 400-on-malformed being a weak enumeration oracle (clean error
  semantics for the frontend matter more than millisecond timing parity on
  syntactically invalid input).
- **Confirmed no conventions broken**: codebase-fit reviewer found zero
  divergences from existing patterns.

## What this doc doesn't cover

- The in-app UI (license card, certificate modal, support nav) — lives in
  the frontend repo.
- The marketing `/support` page — lives in the `marketing` branch of the
  frontend repo.
- License key revocation. We never check whether a stored license key is
  still valid; the `license-invoice` endpoint looks up the customer in
  Stripe at request time, so a cancelled subscription will still show the
  customer's old invoices (which is correct — they did pay at one point).
- Multi-org licensing. One license key per org, as implemented.
- Email backend choice. Inherits whatever `EMAIL_BACKEND` the deployment
  configures.
